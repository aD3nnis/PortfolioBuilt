    How AI Changes These Concepts

    When Claude writes most of the code, writing code stops being the slow part. Deciding what to build, where the boundaries go and whether the result is any good takes its place. Ousterhout's main warning, that complexity builds up one small decision at a time, matters even more now, because an AI can make those small decisions far faster than a person can. Below is how each idea shifts and what's recommended now.

    Ch 3 · Strategic vs. tactical

    AI is the ultimate tactical programmer

    What changesEvery prompt asks for the task at hand to work, so the agent delivers exactly that, quickly. Without a plan, you get tactical programming at machine speed.

    What's recommendedPut the time AI saves into design. Once a feature works, ask Claude to step back: "What would you restructure now that this exists?" Then do that cleanup before moving on.

    Ch 4 · Deep modules

    You own the interface, Claude fills it in

    What changesGenerated code leans shallow: lots of small helpers, pass-through wrappers and config flags that push decisions back onto callers.

    What's recommendedDesign the interface yourself (signatures, contracts, what callers never need to know) and have Claude implement behind it. In review, ask: "Could this interface be smaller and still do the same job?"

    Ch 5 · Information hiding

    Good boundaries are good context

    What changesA model only knows what fits in its context. Information leakage used to cost a human some reading time. Now it means the agent edits one file and misses the three others that share the same hidden assumption.

    What's recommendedTreat deep modules as context management. If a change only needs one module and its interface, the agent can get it right, and you can review it in one sitting.

    Ch 11 · Design it twice

    Designing it twice is nearly free now

    What changesSketching a second or third design used to cost hours, so people skipped it. Now it takes minutes.

    What's recommendedBefore any code, ask for two or three very different approaches, such as a queue versus a synchronous call or one service versus two, with their trade-offs. Pick one, or combine them, and write down why.

    Ch 12–15 · Comments

    Comments are now prompts

    What changesThe agent reads comments, docs and CLAUDE.md as instructions. The "why" behind a design isn't visible in the code, so the model can't work it out on its own.

    What's recommendedWrite the interface comment first, then have Claude implement to match it. Project decisions and "never do X here" rules go in CLAUDE.md so every session starts with them.

    Ch 17 · Consistency

    AI amplifies whatever patterns exist

    What changesAgents copy the code around them. A consistent codebase makes each new change consistent too, and a messy one spreads its mess into every new file.

    What's recommendedClean up one clear reference example of each pattern and point Claude at it. Write conventions down instead of leaving them as tribal knowledge.

    Ch 16 · Modifying code

    Watch for the minimal patch

    What changesWhen asked to fix something, AI usually makes the smallest change that works: a special case here, an extra parameter there. Each patch is reasonable on its own, and together they make the design worse.

    What's recommendedAsk: "If the design had been built with this requirement in mind from the start, what would it look like?" Then review diffs for special cases and shims, not just for whether the tests pass.

    Ch 10 · Define errors out

    Push back on defensive noise

    What changesGenerated code often wraps everything in try/catch, null checks and fallbacks for cases that can't happen. That adds error handling everywhere instead of designing errors away.

    What's recommendedAsk whether an error can be designed out entirely, for example with an idempotent operation, a sensible default or a narrower input type. Then remove the checks that don't protect anything real.

    Patterns · Architecture

    Architecture choices that work well with agents

    What changesA modular monolith keeps the whole system in one repo that an agent can search and test end to end. Microservices and event-driven systems hide the flow across network hops that the agent can't see.

    What's recommendedDefault to a modular monolith. When you do split services, make the contracts explicit and machine-readable (OpenAPI, event schemas) and document event flows, so the agent can reason across boundaries.

    Ch 21 · Decide what matters

    Tests become the spec

    What changesAn agent that can run tests can check its own work, so whoever writes the tests decides what "correct" means.

    What's recommendedWrite or carefully review the tests that capture what matters, like behavior at the interface and edge cases from the requirements. Claude can iterate freely against them. Tests of implementation details just lock in whatever the AI happened to write.

    A recommended workflow when Claude is writing the code

    1. Frame it yourself. Requirements, constraints and what "done" means, in your own words.
    2. Design it twice. Ask for competing designs with trade-offs, then pick one and record why.
    3. Own the interfaces. Write the signatures and interface comments, or edit Claude's draft until they're deep and simple.
    4. Delegate the implementation. Let Claude build behind the interface, with tests it can run.
    5. Review for complexity, not just correctness. Look for shallow modules, leakage, special cases and defensive noise.
    6. Make a strategic pass. Refactor while the context is fresh, before starting the next feature.
    7. Write it down. Decisions and conventions go in CLAUDE.md and comments so the next session starts from them.

    What doesn't change: the engineer is still responsible for the complexity. AI makes code cheaper to write, but the system still has to be understood, and that part is still a person's job.
