A guide for directing the work

Choose a workflow row for the kind of problem. Use the phases to understand the decision you are making now. Click a phase heading or a button below for Claude’s actions, your checkpoint, evidence, and return points.

Short route: for a contained, understood change with a useful check, confirm the problem and approach briefly, change it, verify, inspect the diff, and deliver. Separate spec and plan files are optional.

Full route: expand investigation and record requirements, approach, risks, and dependencies when behavior is unclear, several areas interact, or consequences need investigation. Small code changes can still have large consequences.

If something fails: revisit the affected decision and repeat relevant checks. You do not automatically restart. A phase is a question to answer, not necessarily a document to write.

Bug fix example: connect code to tests

Understand: 1,000 cents split three ways produced [333, 333, 333], totaling 999. Integer division discarded the remainder.

Required: preserve the total. Already established: the sandbox uses whole cents. Proposed choices: keep shares as even as possible, and assign leftover cents to the first people. Confirm these policies rather than silently assuming them.

1,000 cents ÷ 3 people
        ↓ divmod(1000, 3)
base share = 333     remainder = 1
        ↓ distribute the remainder
[334, 333, 333]
        ├─ sum == 1000 → checks that no money is lost
        └─ exact list → checks the chosen allocation policy

[333, 333, 334] preserves the total but uses a different allocation policy. A failed assertion needs interpretation: which promise was broken?

Regression evidence: the same meaningful test fails with the old logic and passes with the fix. This shows it detects the original defect; keeping and running it helps catch recurrence. It does not guarantee the bug can never return.

Scope: unrelated findings can become follow-up work. Decide whether they undermine this fix before expanding the task.

Tools: /map describes a repository’s structure; this close examination of a function and its tests belongs in Review. /spec and /plan can record complex decisions; /walkthrough supports your understanding; /handoff supports continuation.

Alternative routes that can happen in any workflow

Why this structure

The docs describe one loop, not nine workflows. How Claude Code works says every task runs through gather context, take action and verify results, and that tasks use the loop differently: a question may only gather context, a bug fix cycles through all three, and a refactor may need a lot of verification.

  • The columns are that loop, with four phases added. Understand, Change and Verify are the loop's three phases. Plan comes from Common workflows (plan before editing). Review and Ship come from the review article and Best practices (a reviewer who didn't write the code). Start comes from how sessions work. Close comes from the docs' way of carrying work across sessions: a named session you can resume, plus CLAUDE.md and auto memory. The handoff file is your setup's addition.
  • The rows are recipes the docs already give. Common workflows has recipes for exploring a codebase, fixing bugs, refactoring, tests and docs. Best practices builds a feature from a spec and covers large mechanical changes with /batch. Extend Claude Code gives the setup triggers. Two rows have no docs recipe. Hotfix is built from the review article. New project is assembled from the docs' steps that still work in an empty folder: Quickstart and every recipe assume a project already exists.
  • Putting recipes on a shared grid is my design choice. It shows where two workflows differ and where they're the same, which a list of recipes doesn't.

How to say it in an interview

"The docs give one agentic loop and a set of task recipes. I laid the recipes onto the loop's phases so you can see where workflows differ, and every step cites the page it came from. Where I made a choice the docs don't, it's labelled with the reason."

What checking against the live docs changed

  1. Secret files now use deny rules such as Read(./.env), which hold in every permission mode (Best practices). The old map used only a hook.
  2. Pushes now use an ask rule on git push plus branch protection (Best practices). The old map used a hook.
  3. The teal band is renamed "Enforced by Claude Code", because it holds deny rules as well as hooks. Best practices calls these deterministic instructions.
  4. Start no longer says the newest handoff loads by itself. It loads only because your CLAUDE.md tells Claude to read it, so it's tagged as your setup.
  5. Feature now starts from Best practices' "Brainstorm with Claude first": Claude interviews you, writes SPEC.md, and you build from it in a fresh session.
  6. Large migration was mostly my synthesis. It now follows Best practices (/batch, and try about three files first) and Extend Claude Code (a dynamic workflow cross-checks results).
  7. /simplify no longer appears as a cited step. None of the pages checked mention it, so it's tagged as a design choice on Refactor.
  8. New project was added on 14 Nov 2026. Best practices, Common workflows, Memory, Extend Claude Code and Quickstart were read that day, and none has a from-scratch recipe. Three things they do say set the row's order: /init reads your codebase, so it runs after the skeleton exists (Memory). You don't need to configure everything up front (Extend Claude Code). Worktrees need at least one commit (Common workflows), so the row ends at the first commit.
  9. Understanding an existing repo uses routes, not a tenth row (15 Nov 2026). Explore now reads in the order Common workflows gives, and routes into New project at Verify when the repo isn't set up for Claude. New project's Verify to Close is named the Claude-ready baseline.
